# Demo deployment — Togo portal on Vercel + Neon

The `developAgentic` branch deploys the Django portal as a public,
fully-populated demo. Everything in it is fictional: village names are built
from Togolese syllables rather than copied from the gazetteer, people and
amounts are generated, and the photographs are procedurally drawn SVG scenes.
Nothing here is real household or project data.

## What the demo contains

Generated by `python manage.py seed_togo_demo` from a fixed PRNG seed, so the
same seed always rebuilds exactly the same portal:

| | |
|---|---|
| Regions | 3 (Savanes, Kara, Centrale) |
| Prefectures / communes / cantons | 16 / 23 / 67 |
| **Villages** | **336** |
| **Local priorities** | **1 344 — exactly 4 ranked priorities per village** |
| Sub-projects | ~365, one per funded priority |
| Photos | ~1 480, attached to villages and works |
| Planning-cycle tasks | 5 712 (4 phases × 2 activities × 2–3 tasks per village) |
| Funding programmes | 5 |
| Investment packages | 20, spread across the approval states |
| Accounts | 8 |

Every village carries a population breakdown, GPS coordinates, an
infrastructure inventory, a CDD planning cycle stopped at a realistic point,
a photo library and a cover image.

## How it is deployed

`api/index.py` exposes the Django WSGI app to Vercel's Python runtime, and
`vercel.json` rewrites every path to it. Static files are served by WhiteNoise
from inside the app — there is no nginx and no `collectstatic` step, so
`WHITENOISE_USE_FINDERS` is enabled whenever `staticfiles/` was never built.
Uploads fall back to Django's filesystem storage because no S3 bucket is
configured; the demo's imagery is shipped as static files instead, and
`Attachment.url` simply points at `/static/images/demo/...`.

The Python runtime is 3.12, which forced three dependency changes:
`numpy`/`pandas` off their 1.23/1.5 pins (no 3.12 wheels) and an explicit
`setuptools` pin (3.12 dropped `pkg_resources`, which the pinned
`djangorestframework-simplejwt` imports).

### Continuous deployment

- `.github/workflows/ci.yml` — pull requests into `developAgentic`: migrate a
  throwaway Postgres 16, seed it, and render every major page.
- `.github/workflows/deploy-vercel.yml` — merges into `developAgentic`: the
  same verification, then migrate Neon, then build and deploy through the
  Vercel CLI.

Vercel's own Git integration is switched off (`github.enabled: false`) so this
workflow is the only deploy path; otherwise every push would deploy twice.

A merge **migrates but does not re-seed** — re-seeding would discard whatever
state the demo has accumulated. To rebuild the dataset, run the workflow
manually (*Actions → Deploy demo to Vercel → Run workflow*) with **reseed**
ticked.

### One-time setup

This is already done for `ldp-togo-demo`; the steps are kept for rebuilding
it elsewhere.

1. Link the Vercel project from this directory (the Django project root, not
   the repository root):

   ```bash
   npm i -g vercel
   cd cosomis
   vercel link
   cat .vercel/project.json   # -> orgId and projectId
   ```

2. Provision the database through the Vercel Marketplace — no separate Neon
   account is needed, and the integration writes `DATABASE_URL` (plus the
   `POSTGRES_*`/`PG*` variants) into the project's Production environment:

   ```bash
   vercel integration add neon --name ldp-togo-demo-db -e production --plan free_v3
   vercel env pull .vercel/.env.production.local --environment=production
   ```

   The integration also drops agent-skill docs (`.agents/`, `.claude/skills/`,
   `skills-lock.json`) into the directory; they are ignored and can be deleted.

3. Set the remaining Vercel environment variables (Production):

   | Variable | Value |
   |---|---|
   | `SECRET_KEY` | a long random string |
   | `ALLOWED_HOSTS` | `*` |
   | `DEBUG` | `False` |
   | `PROGRAM_NAME` | optional, overrides the branded programme name |

4. Add the GitHub Actions secrets (*Settings → Secrets and variables →
   Actions*):

   | Secret | Value |
   |---|---|
   | `VERCEL_TOKEN` | https://vercel.com/account/settings/tokens |
   | `VERCEL_ORG_ID` | `orgId` from `.vercel/project.json` |
   | `VERCEL_PROJECT_ID` | `projectId` from `.vercel/project.json` |
   | `DATABASE_URL` | the same Neon connection string |
   | `SECRET_KEY` | the same secret key |

5. Seed the database once (about 2½ minutes over the wire to Neon's
   `us-east-1`):

   ```bash
   cd cosomis
   DATABASE_URL='<neon url>' python manage.py migrate --noinput
   DATABASE_URL='<neon url>' python manage.py seed_togo_demo --reset
   ```

### Deploying by hand

```bash
cd cosomis
vercel pull --yes --environment=production
vercel build --prod
vercel deploy --prebuilt --prod --yes
```

Two things about the prebuilt flow are easy to trip over:

- `vercel build` traces the function's files from everything that
  `excludeFiles` (vercel.json) leaves in, but `vercel deploy --prebuilt`
  uploads only what `.vercelignore` leaves in. Anything in the second list but
  not the first is referenced by the build and never uploaded, and the deploy
  fails with `ENOENT`. Keep the two lists identical.
- The exception is `_uv/`: the Python builder downloads its own `uv` binary
  there on every build and maps it into the function even though
  `excludeFiles` names it, so it must stay uploadable (it is git-ignored).

## Checking a deployment

`python manage.py demo_smoke_test` signs in and requests every major page —
the investment catalogue, all five administrative-level profiles, the
dashboards, the gallery, the CDD funnel and the admin — failing if any of them
does not render. CI runs it on every pull request and every merge.

## Known gaps

- **Excel export** (*Export file* on the dashboard summary tables) does not
  work, and did not before this branch: the button is a plain form POST while
  the view requires an AJAX request, so it returns 404 without ever running.
  The view also writes into `static/`, which is read-only on Vercel, so it
  would need reworking to stream the file rather than save it.
- **CouchDB/Kobo sync commands** (`1_syncvillagegeneral` and friends) are not
  used by the demo and have no server to talk to.
- **Mapbox** tiles need `MAPBOX_ACCESS_TOKEN`; without it the map views render
  but show no basemap.
